1. High priority: Monkey Knowledge strategies can save successfully and disappear on reload
References: [editor validation (line 3043)](C:/Users/rodge/OneDrive/Desktop/BTD6_Guide/btd6_guide.pyw:3043), [override loading (line 284)](C:/Users/rodge/OneDrive/Desktop/BTD6_Guide/btd6_guide.pyw:284).
The editor and importer validate with the current Monkey Knowledge setting. The loader validates saved overrides with the default setting—Monkey Knowledge disabled.
I reproduced this with a modified Medium strategy:
1. Change its opening to Gwendolin at $725.
2. Validate with Monkey Knowledge enabled: passes.
3. Save the override: succeeds.
4. Reload: the loader rejects the override and restores the bundled Sauda strategy.
The rejected override is also removed from the in-memory override collection. A subsequent save could overwrite the override file without that strategy.
Recommended fix: store requirements with the strategy, such as:
"requirements": {
  "more_starting_cash": true,
  "free_dart_monkey": false
}
Use those requirements consistently during editing, loading, generation, import, and export. The current UI setting should determine whether the user can follow a guide, not whether that guide survives loading.
2. High priority: community import processes malformed data before validating it
Reference: [btd6_guide.pyw (line 2289)](C:/Users/rodge/OneDrive/Desktop/BTD6_Guide/btd6_guide.pyw:2289).
The importer assigns IDs before checking the strategy’s schema.
I executed the actual import method with these inputs:

"steps": null	TypeError: 'NoneType' object is not iterable

These should produce ordinary import-error messages.
The importer also allows users to accept validation failures through “import anyway.” That activates a strategy immediately even though the loader may reject it at the next restart.
Recommended fix:
- Validate field types before normalization or ID assignment.
- Separate structural errors from gameplay warnings.
- Never activate structurally invalid content.
- If incomplete guides are allowed, save them explicitly as drafts and support that status consistently on reload.
3. Medium priority: mixed explicit and automatic tower IDs can overwrite a tower
References: [ID generation (line 107)](C:/Users/rodge/OneDrive/Desktop/BTD6_Guide/btd6_replay.py:107), [duplicate checking (line 254)](C:/Users/rodge/OneDrive/Desktop/BTD6_Guide/btd6_replay.py:254).
Explicit duplicate IDs are rejected, but automatically generated IDs are not checked against existing IDs.
Confirmed reproduction:
1. Place a Dart Monkey with explicit ID dart_monkey_1.
2. Place another Dart Monkey without an ID.
3. Both placements succeed.
4. The board contains one tower, because the generated ID overwrites the first.
This is relevant to mixed imported and manually edited strategies.
Recommended fix: generate an unused ID, then check uniqueness regardless of its origin. Prefer UUIDs for newly created tower instances and require explicit IDs after migration.
4. Medium priority: schema validation still misses important fields
References: [replay field handling (line 229)](C:/Users/rodge/OneDrive/Desktop/BTD6_Guide/btd6_replay.py:229), [database loading (line 226)](C:/Users/rodge/OneDrive/Desktop/BTD6_Guide/btd6_guide.pyw:226).
Additional probes found:
- A list-valued tower_id crashes validation with TypeError.
- A numeric placement passes validation.
- A list-valued step_id passes validation.
- "Various" is accepted for an Upgrade action.
The latter can set a tower’s upgrade state to None, rather than a valid three-tier tuple.
The database loader checks map and strategy containers, but still does not validate their complete contents before assigning the live database.
Recommended fix: define action-specific schemas:
- step_id and tower_id: nonempty strings.
- placement, details, and other displayed text: strings.
- Place/Upgrade: concrete legal upgrade tuples.
- Composite instructions: explicit action types rather than "Various" bypasses.
- Step IDs: unique within a strategy.
Validate candidate data fully before replacing live state.
5. Medium priority: saved and shared guides do not record their execution assumptions
Reference: [btd6_guide.pyw (line 2214)](C:/Users/rodge/OneDrive/Desktop/BTD6_Guide/btd6_guide.pyw:2214).
The new sharing format includes a schema version, map, difficulty, and strategy, but does not record the Monkey Knowledge assumptions used to validate it.
Consequently, two users can import the same file and get different validation results based on their local toggle. Markdown and HTML also use the strategy’s stored starting_cash, which may remain $650 while validation permits $850.
Recommended fix: make requirements part of the exported strategy and display them clearly:
- Required starting cash.
- Required perks.
- Game-data version.
- Validation status and playtest evidence.
This should use the same metadata that fixes override reload behavior.
What I would change next
Prioritize these regression tests:
1. A Monkey Knowledge-dependent guide survives save, reload, and export/import.
2. Malformed imports return diagnostics without exceptions.
3. Mixed explicit/generated tower IDs never collide.
4. Every accepted strategy is safe for rendering and replay.
5. Draft imports remain drafts after restarting.
The remaining architectural concern is still data authority: passing the application’s model is not proof of a winning strategy. The database currently contains 87 Verified, 174 Structurally Validated, and zero Playtested entries. Continue distinguishing software validation from demonstrated gameplay results.
My assessment: the replay and persistence foundations are substantially better now. The next release should concentrate on consistent strategy requirements and strict input boundaries, rather than adding more features before saved and shared guides behave reliably.
